上游原始状态

针对 bytedance/LatentSync 与 ByteDance/LatentSync-1.6 未经修改的发布版本。以下为直接核查各上游项目 LICENSE 文件与仓库 tag 后的结论。

核心缺陷

许可证声明与实际内容不符
仓库以 Apache-2.0 分发了无授权的第三方代码实质违规

根目录 LICENSE 为 Apache License 2.0，覆盖全仓库。但仓库内含三份改编自无任何许可证项目的代码——原作者从未授予任何权利，ByteDance 因而既无权分发，更无权将其重新许可为 Apache-2.0。

该矛盾在 README 中即可见：致谢段落明写 “Some code are borrowed from MuseTalk, StyleSync, SyncNet, Wav2Lip”，而 StyleSync 无 LICENSE 文件、Wav2Lip 亦无 LICENSE 文件且 README 声明限非商业用途。

专项分析

上游权重本身是否合规

ByteDance 在训练与数据管线中使用了无授权代码与来源存疑的评估权重。核心问题是：由此产出的 latentsync_unet.pt 是否因此受污染，进而影响我方的使用权？

按组件在流程中的位置分层

判断的关键不是「用没用过」，而是「有没有进入梯度路径」——即是否有第三方的表达被写入模型参数。

① 梯度路径内真正塑造权重
  • recon_loss — 纯 MSE，无第三方组件
  • sync_loss → StableSyncNet：ByteDance 自有架构、自训权重，Apache-2.0
  • lpips_loss → LPIPS（BSD-2）+ torchvision VGG16（BSD-3）
  • trepa_loss → VideoMAEv2（Apache-2.0）

梯度路径中不含任何无授权组件。尤其注意：训练损失使用的 SyncNet 是 ByteDance 自己的 StableSyncNet，与来源存疑的 Oxford syncnet_v2.model 无关。

② 数据预处理与筛选决定训练集构成
  • 人脸对齐 → affine_transform.py（StyleSync 血统，无许可证）
  • sync_av.py → 以 SyncNet 置信度筛除视频、校正音画偏移（syncnet_v2.model）
  • filter_visual_quality.py → hyperIQA 打分筛除低质视频（koniq_pretrained.pkl）

这些组件只决定「哪些视频进入训练、如何裁剪」，其自身的代码表达并未进入模型参数。数据筛选器对权重的关联比损失函数更弱——它不提供任何梯度信号，只做取舍。

③ 训练后评估零影响
  • validation 同步置信度（syncnet_v2.model，原 train_unet.py:489）
  • FVD（i3d_torchscript.pt）、hyperIQA 画质分

全部在 no_grad 下执行，仅用于绘制曲线与论文指标，对权重无任何影响。

结论

权重的可用性不因上述组件受影响但非无风险

版权路径：要使这些组件的权利人触及权重，需先证明权重是其代码的衍生作品。数据筛选器与评估器没有任何表达进入参数；affine_transform 产出的是裁剪后的图像，而非代码表达的复制。在最接近的判例中，Andersen v. Stability AI 法院驳回了「模型本身即衍生作品」的理论（该案针对训练数据，庭审定于 2026-09-08）。

合同路径：StyleSync 与 Wav2Lip 的条款中均无反蒸馏条款（即「禁止用本软件训练其他模型」）。此类条款在 LLaMA、OpenAI ToS 中普遍存在，其存在本身即说明：单靠版权法够不着这件事，必须另行以合同约定。Wav2Lip README 中的商用禁止针对的是其自身的预训练模型（因训练于 LRS2），并非用其代码训练的其他模型。

传导路径：纵使 ByteDance 因分发无授权代码被追责，救济指向 ByteDance。原作者对权重无所有权基础，且我方与其并无合同关系。ByteDance 对权重的 OpenRAIL++ 授权处分的是其自身权利，为 perpetual 且 irrevocable，不因其对第三方的违约而失效。

真正的权重风险来自别处按量级排序
风险 1
上游训练数据来源不明。配置指向 ByteDance 内部路径，且仓库含 tools/download_web_videos.py，部分数据可能来自网络抓取。OpenRAIL++ 第 IV 节以 “AS IS” 提供，明确不保证 non-infringement，无 indemnification。此项无法通过本项目内的改动消除
风险 2
OpenRAIL++ 使用限制未向下游传递。可控，见下方义务清单
风险 3
无授权组件的传导 — 依上述分析，为三者中最低
2025 年以来的判决（Bartz v. Anthropic、Kadrey v. Meta）确立的分野是：合法获取的语料训练可主张合理使用，盗版语料则否。举证焦点因此转向数据来源。这使风险 1 的量级显著高于风险 3——大客户尽调时会问训练数据来源，而不会问用了什么评估脚本。

遗留义务

OpenRAIL++-M · 需法务动作

以下 5 项均源自 UNet 权重的许可证，是本次核查唯一需在产品与合同层面落实的事项。

  1. 向下游传递使用限制。分发权重、SDK 或微调产物时，须在自有协议中原样纳入 Attachment A 的 11 条限制。权重无法被重新许可为 Apache-2.0 或 MIT。
  2. 随附许可证副本，并显著标注修改。微调、蒸馏、量化均属修改，需注明。
  3. 产品内建肖像同意流程。Attachment A 第 3、4、5 条禁止未经同意的冒充、有害虚假信息与诽谤骚扰——对唇形同步产品，这要求上传素材时有授权确认环节与可执行的滥用处置流程。
  4. 接受无侵权担保。许可证以 “AS IS” 提供，明确不保证 non-infringement，亦无 indemnification。对应上文风险 1。
  5. 预备来源问询的答复。OpenRAIL++ 非 OSI 认证开源许可，部分企业采购的自动化扫描会标记为受限而触发人工审查；大客户亦可能要求训练数据来源声明与赔偿条款。

本清单基于对各项目 LICENSE 文件、GitHub API 返回的 SPDX 标识、模型仓库 license tag 与官方声明的直接核查，来源链接均已在文中标注。哈希与字节数取自本地 checkpoints/ 实际文件。

本文档为工程侧的合规梳理，不构成法律意见。OpenRAIL++ 义务的具体落地条款、以及上游训练数据来源风险的承担方式，建议由法务确认。
